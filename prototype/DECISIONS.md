# 原型验证约定

## 已确认的产品方向

- 目标优先级：stars/传播 > 持续使用 > 求职展示。
- 通用网页填表加速工具；秋招网申作为首个真实场景。
- 首发同时服务 Codex 和 Claude Code，允许安装浏览器扩展或本地连接组件。
- 2026-09-21 更新：当前阶段只用 Codex 测试，Claude 验证暂停；保留其接入代码。用户批准目标级计划实验并借鉴 Jev，仍沿用现有模型登录。
- 资料来自已有 Agent 上下文/文档，第一版不建立专用个人资料库。
- 默认复用已有 Agent 的模型能力，不引入额外模型 API Key。
- 第一阶段先证明明显提速。暂定目标：至少三种不同实现的表单，正确率不降低，完整耗时中位数减半。

## 当前实验回答什么

1. 一套执行核心能否通过真实浏览器扩展和标准 MCP 工作？
2. 输入事件是否进入页面自身的数据状态？过期引用会不会误填？
3. 在预先给定正确映射时，执行层是否比合理的批量脚本更快？
4. Codex 是否能够发现工具、填写虚构资料并检查结果？Claude 测试暂停。
5. 同一 Codex 下，将动态填写的多个工具往返合并为一个有界计划，是否降低完整耗时？能否优于一次生成整段脚本？

预先提供字段映射是执行层实验的边界，不代表完整产品已经能理解陌生表单。没有用人为的模型等待时间制造速度优势。原生日期和下拉不代表复杂日期选择器/自定义控件已经支持。

## 基线与成功标准

- `single-field-control`：每字段一次请求，同一执行器与校验策略。仅解释减少往返可能带来的收益，不用于产品提速宣传。
- `playwright-batch-script`：单个外部脚本内使用合理的 Playwright locator 调用，处理相同动态依赖；没有逐操作 LLM 请求。
- `extension-batch`：观察字段，构建批量计划，通过真实 Chrome 扩展执行，按需重新观察。
- 三者均在页面加载和连接完成后开始计时，计入观察/执行/等待及独立页面状态校验。启动与预先给定映射时间不计入。
- 每方式预热一次，五次重复，交替执行顺序；报告中位数与每次正确性。DOM 值和页面自身事件状态必须同时正确，提交次数为零。
- 宿主 smoke test 仅验证接入，不是原生浏览器速度比较。模型默认配置和一次运行波动不可用于两端排名。

## 仍需验证

- 用户实际招聘页的具体系统和控件结构，尚未提供。
- 两端原生浏览器的合理批量用法（尤其 Claude `browser_batch`）与我们工具的端到端对比。
- 自定义下拉、重复组、页面重渲染如何影响模型回合数、成功率与人工修正。
- 日常 Chrome 上由用户点击扩展获得 `activeTab` 的完整安装体验；自动化测试采用已获本地测试源权限的隔离浏览器，不能代替该体验。
- 跨宿主同时操作、断线恢复、异步校验、权限范围变化等生产要求。

## 结论使用边界

如果执行层比优化后的批量脚本更慢，应明确报告，不能改用逐字段对照包装提速。下一阶段优先测真实任务中模型往返/失败恢复的占比；只有证据支持时才扩大为完整产品。公开传播前需要可复现的端到端证据。

## 持续目标的本轮结论

用户已授权持续探索减少模型往返，直至实际效果达标。一次调用只是必要优化之一；资料引用还能避免模型重抄字段值。本轮已有映射 JSON 的小表单从约 32.5 秒降至 19.1 秒，但可复用脚本已达到约 23.2 秒，不能宣称自研浏览器核心有稳定两倍优势。继续优先验证原始资料到陌生页面的首次映射、真实控件观察和失败恢复，保持成熟批量/缓存脚本作为强基线。完整目标未完成。

## 文档绑定与预取的本轮补充

不再要求预先把 JSON 映射到网站字段：有限格式 Markdown 被拆成来源片段，Codex 现场匹配英文字段，文本在本地复制。九次任务全部正确；省去一次显式上下文调用，中位耗时约减少 16%。这支持继续优化数据流，但未达到完整两倍目标。真实 Lever 的只读复查显示标签/分组改善，未进行真实申请填写。引入官方 Playwright MCP 0.0.82 作为更强基线，并同样允许来源引用和预取，不能靠压低对照工具能力来论证项目。

官方强基线也表明：预取并不保证更快，若脚本误解快照标签会引入恢复。验证要求对齐后的唯一双方一次调用成功配对是 26.98 s vs 41.65 s，其余脚本轮次受审查或定位超时影响；不使用失败造成的 3.82× 中位数差做宣传。下一轮增加独立框架和复杂控件，保留已审核的可复用脚本/工具作为对照，而非继续扩大同一种简单 fixture 的采样。

## 框架控件与重复组的补充

React/Radix 独立本地样本已验证 select-only Portal 下拉、依赖控件替换、明确 ARIA 校验状态与重复组；69 项浏览器/MCP功能检查通过。修复旧执行器在 700 ms 校验完成之前误报成功的问题，速度必须以真实完成为前提。输入型 autocomplete 和任意异步业务仍不在已验证范围。

同一执行器复用重复组模板，完整中位耗时 33.28 → 24.29 s，6/6 正确，约减少 27%。修正资料/快照接入后的官方工具对照也是 6/6 最终正确；每次生成脚本的三次尝试均遇到相同 30 秒定位超时并恢复，不能用其 136.42 s 对原型 24.64 s 宣称稳定倍数。下一步用已审核的通用 Playwright helper 隔离“重复写代码”的成本，决定是否需要维护自研执行核心。详细边界、失败和原始记录见 FRAMEWORK-VALIDATION.md。完整目标保持未完成。

## 动作后端替换的补充

已给 Playwright 提供通用 helper，并共用来源接口、观察器与目标协调器。两边完整模型可见工具相同；6 次 Codex 任务均一次调用成功，扩展 24.02 s、Playwright 27.07 s。它是后端替换实验，不能冒充独立竞品对照，但足以否定目前已有自研动作层倍数优势的说法。

后续检查还发现 helper 在弹层期间标签/分组变化时缺少选择前保护，现已修复；最终版本未重新计时，原测量源码已归档。下一步增加输入型搜索建议等独立控件，优先验证共享任务协议在复杂状态中的价值，暂不因单页速度替换日常浏览器部署方案。见 BACKEND-SUBSTITUTION.md 和 ADR-0005。原多类表单完整流程明显提速的目标继续保留。

## 异步搜索控件的补充

已在 Playwright 后端加入 React Select 5.10.2、带 classNamePrefix 的单选 DOM 适配。区分查询字符串与选中实体，等待异步结果，仅选择唯一可用精确项，并核对最终显示/查询清空/弹层关闭。扩展路径继续明确不支持输入型 combobox。

15 项新检查与实际 MCP 接入通过；3 次 Codex 全部一次调用完成，10 目标/次、两段经历、3 次异步搜索，中位 29.05 s，30/30 独立应用状态正确、零提交。本组是独立控件实现的迁移检查，没有速度对照，不能据此宣称两倍收益。Greenhouse 仅观察到类似 DOM，未进行真实申请填写。

下一步重点是资料与选项写法不一致时的可控回退，以及任务的未解决字段覆盖；当前接口把来源文字、搜索词和目标标签合在一起，遇到无结果时尚不能自由改写查询。需要在保留事实来源的同时分离“用于发现选项的查询”与“最终填写的已观察选项”，避免无限回合或静默猜选。完整目标仍未完成。
