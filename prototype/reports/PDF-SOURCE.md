# PDF 原文到同一次填写计划

2026-09-21。可选实验；不是任意简历解析器或完整申请提速证明。

## 结果

原型可以直接接收受限的纯文字 PDF，不必先由人或模型重写为键值 Markdown。当前 Codex 仍负责理解和匹配；本地提取空间文字片段并提供页码、坐标。同一次 `form_apply_bindings` 可以引用精确原文，或按顺序连接同一段落的完整行。没有增加用于整理资料的模型 API 调用。

最终批次 `1789965949436`，两次实际 Codex CLI 任务均完成 10 个已知目标：姓名、邮箱、国家、城市、学历、两段学校/专业、完整两句个人介绍；校区限定保留，缺失到岗日期留空并报告，零提交/上传。两份 PDF 视觉内容与布局相同，仅 PDF 绘制指令次序相反，**不是两种独立招聘任务**。

| 输入 | 单独提取 | 启动准备（含提取） | Codex 会话 | 总时间 | 工具调用 |
|---|---:|---:|---:|---:|---:|
| 双栏 PDF | 91 ms | 652 ms | 47.802 s | 48.457 s | 2 |
| 绘制顺序倒置 PDF | 83 ms | 645 ms | 55.335 s | 55.985 s | 2 |

两次都是先查询中文“杭州”无结果，再改为 Hangzhou。邮箱通过 `{sourceId,quote}` 从混合行提取，个人介绍通过两个完整片段 ID 连接，均未因 PDF 另开整理回合。七个相关运行时文件测前/后 hash 一致；两个输出和最终文字已逐份核对。

这不是速度对照：每种输入只一次，且部分回归检查同时运行。不能拿这两个数与旧 Markdown、修复前失败或其他提交的时间相减，宣称净提速。它只证明在该输入中资料整理不必额外占一个模型回合。中文搜索回退的第二次往返仍存在。

## 从反例得出的接口

普通 `pdfplumber.extract_text()` 把双栏同一高度文字合并，例如：

```
candidate@example.test | 中国 南方示例学院
意向工作城市：杭州 Southern Example College
```

因此不把整份 PDF 的扁平文本直接当成可靠 Markdown 字段。实验提取器按公开文字坐标保留横向片段，较大空隙分隔，给出 page/bbox。它不推断“姓名”“学校”或左右栏阅读顺序；模型仍需理解这些位置与文本。24 pt 空隙和 3 pt 行阈值只是当前启发式，不保证任意版式正确。

PDF 会话的文本绑定有三种形式：

- `"s1"`：复制整个来源片段。
- `{"sourceId":"s3","quote":"candidate@example.test"}`：只复制该片段中唯一的精确连续原文，回执保留起止偏移。
- `["s16","s17"]`：按顺序复制 2–12 个不同完整片段，以换行连接；仅同页，回执保留全部来源 ID。是否同一逻辑段落仍由模型判断，不把任意几何邻接当语义证明。

这些新增形式只在 PDF 会话的 MCP schema 开放。普通 Markdown 会话保留字符串来源 ID，不增加这段提示。下拉、复选等仍要求普通来源 ID 和原有候选选择协议。所有写入前检查源文件字节 hash；不重跑模型或每次重提取 PDF。

## 保留的失败与修复

首批 `1789965738330` 第一份 PDF 最终正确，但耗时 106.615 秒、7 次调用、3 次 `INVALID_SEARCH_CONDITION`。不能当作合法的慢基线。查出既有预检分支使用 `choice?.search` 判断条件对象，而 JavaScript 字符串也有 `.search` 方法；新增原文引用开启更早的整体预检，使原生选项字符串触发这个旧问题。定向测试先失败，再补 `typeof choice === 'object'` 后通过。首批第二任务主动中止以修复已定位的问题；当次报告保存错误，不能当作一个完成样本。

另一项负例发现任务记录只比较 sourceId，可能把同一片段里另一个引文认作相同依据。现在引文偏移与连接 ID 列表均进入目标身份及回执记录；定向测试从失败转为通过。此前中文 Markdown 错误提示被新读取层改成英文，导致旧检查失败；已恢复对应的中文提示，而非放宽旧断言。

最终 63 项相关检查全部通过：PDF/引用9、条件选择11、独立分组14、Markdown/PW8、companion11、离线入口10。除此之外，上述两次实际 Codex 任务通过独立页面应用状态 oracle；不是只检查返回的 complete 标志。

## 使用、依赖和限制

见 README 的 PDF 实验入口。显式 `AFA_PDF_SOURCE=1`；Python 解释器由 `AFA_PYTHON` 指定，默认 python3。仅本地 pdfplumber，无新增模型 API Key。测试环境：Python3.12.14、pdfplumber0.11.9、pdfminer.six20251230、Node26.8.1、Playwright1.63.0；fixture由ReportLab4.4.9/Pillow12.3.0生成。`requirements-pdf.txt` 锁定顶层提取库，未宣称跨平台完整依赖锁定。

最多5MB、10页、300片段、10万提取字符；提取子进程15秒超时、2MB输出缓冲。含图像（包括简历照片）、扫描件、旋转文字、无文字页拒绝处理；加密或无法解析的PDF返回错误。不做OCR、不支持DOCX、附件上传、服务器校验或跨页申请。有限输入支持仍远小于真实简历覆盖范围。

原文精确匹配只能证明字符来自文件，不能证明其语义使用正确；摘掉否定词、错把另一个项目的时间当作当前项目，仍需要模型判断和最终核对。文字提取与原页面视觉也可能不一致。测试 PDF 经 PDFium 渲染逐页检查；当前捆绑 Poppler 因缺少 Adobe-GB1 映射配置把 CJK 页面渲染为空白，故未把其空白预览作为无文字证据，也未修改已安装技能或系统配置。PDFium 显示的两份文本页一致，扫描样本显示图像文字并被提取器明确拒绝。
