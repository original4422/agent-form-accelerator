# 回执投影：少返回重复状态，是否就更快？

2026-09-21。独立分组实验后，浏览器执行时间基本不变，新回执的尾部阶段反而变长。本轮隔离工具返回内容，检验减少重复信息能否改善完整 Codex 耗时。

## 改动与保留的信息

新增可选 `AFA_RECEIPT_MODE=changes`，默认仍是完整回执。只在全部请求目标或实际执行子集已核验时生效，执行器、等待、实际填写、来源检查及最终回读完全不变。

- 整页 observation 改为相对上次已发布页面的字段/元数据增删改、字段顺序及基准 hash。新增问题、被移除的控件、选项和状态变化都保留，客户端可恢复原快照。
- task 中重复的已验证目标行替换为 plannedCount/verifiedCount；所有 unresolvedTargets 逐项保留，包括已经消失的城市控件。
- 每个目标的 expected/actual 验证证据、来源绑定、coverage、候选选项、条件选择、失败原因及限制保持不变。
- 缺少上下文、页面身份变化、重复 ref 或执行结果未核验时，返回完整结果。已分组压缩的上下文暂不应用 delta，以免混淆上下文基准；默认接口行为不变。

MCP 会话保留完整观察和任务记录，只投影宿主收到的数据。`form_context` 仍可读取完整上下文，不用恢复结果驱动浏览器写入。

## 正确性验证

7 项检查通过：新增/删除字段、属性删除、顺序和控件变化可精确重建；错误基准拒绝恢复；URL/文档/重复ref回退完整结果；未知错误和未验证写入回退；所有未完成项、候选及证据不变；JSON wire 规范化；已有真实页结果回放。

真实 Greenhouse 两种回执的 stdio/MCP 检查均通过。变化回执恢复出的字段/控件与新的完整 DOM 观察一致，10 项通过独立公开 DOM oracle，4 项未完成在上下文刷新后仍保留，零提交。旧 observed/conditional 两种 MCP 接入也通过。

第一次真实页检查误将 JSON 中不存在的属性和内存对象中值为 undefined 的属性视为差异，初始报告保留为 `receipt-provider-initial-failure.json`。修正为比较序列化后的数据后通过，运行时未因此改动。

功能检查时，两种完整工具回执约 14,162 / 8,582 bytes，缩小约 39.4%。这只是传输体积，不能据此宣称同比提速。

## 计时协议

`codex-receipts.mjs` 固定 independent 分组机制，交替比较 full/changes、changes/full、full/changes 三对。两边初始上下文、工具说明/schema、提示、权限、浏览器和验证标准相同，只切换返回内容投影。计入 Codex 启动、规划、工具审查/调度、执行、最终回复和退出；公开页面加载及元数据预检不计时。

全部输入仍在网络冻结后使用虚构资料。两边都需核验同样 10 项，并如实报告 4 项远程查询、隐私确认与附件缺口。此次仍不是完整申请或在线服务接受验证。

源码冻结清单：`source-hashes-receipts-measured.json`。各次宿主结果与源指纹保留，不以回执字节数或局部工具耗时替代端到端结果。

## 一次加载中断与恢复

前三次计时完成后，第四次在 `page.goto` 遇到 ERR_CONNECTION_CLOSED，尚未启动 Codex，原驱动立即结束。单独只读浏览器探测同样失败；随后普通 HEAD 请求得到 HTTP 200，恢复运行时浏览器也成功加载。没有更改浏览器、代理、请求头或访问权限。

驱动增加了显式续跑：仅允许恢复这种已确认发生在宿主启动前的连接关闭错误，保留失败行并跳过已经完成的三个任务。之后只运行余下三个任务，未重复选择样本。中断记录 `1789960755528` 不计入 Codex 时延，因为页面加载原本就被排除在计时范围之外。该中断使第二对间隔更长，进一步限制了小幅时延差异的解释。

初始控制脚本归档在 `source-snapshots/receipts-measured/codex-receipts.mjs`；122 个被测源/依赖指纹按归档映射核验一致。浏览器执行、协议运行时、提示及每次实际宿主任务的驱动在整个测试期间未改动，变更仅用于继续未启动的任务。原始七次尝试均保留，六次进入宿主计时。摘要见 `codex-receipts-summary.json`。

## 调整下一步

最近两轮说明，减少必须由宿主重新决定的阶段比减少重复返回字节更值得优先投入。接下来应把已验证的来源绑定、条件计划与独立分组接入可实际启动的浏览器入口，保留现有执行后端，不再另造动作引擎。

目前先进路径仍限定在隔离测试 provider，日常扩展不支持输入型 autocomplete。优先补这个可试用缺口，再根据实际表单反馈处理解析、登录状态与完整流程；不能用本轮部分离线填写代替完整申请验证。
