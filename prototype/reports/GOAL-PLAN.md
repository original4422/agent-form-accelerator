# 目标级计划：Codex 端到端对照

2026-09-21。用户批准从第一性原理继续验证，只使用 Codex；借鉴 Jev 的分工，不增加模型 API Key。

## 要检验的假设

完整耗时可拆为：启动与上下文准备 + 各次宿主决策/工具往返 + 浏览器执行 + 最终验证。

上一轮证明固定等待解释了本地执行器的大部分劣势，但即便把约 160 毫秒执行时间降至零，也不能让三十多秒的完整任务减半。本轮把变量移到模型往返粒度：对预期内的动态变化一次生成计划，由扩展内部观察、绑定、执行；出现新语义问题才返回 Codex。

底层填写方法、原有等待、输入事件和原子步骤回读仍然保留。并未用删除校验换取速度。

## 实现

`form_execute_plan` 接受初始快照、URL、最多 8 个明确阶段：

- `fill`：精确分组名、标签、用户提供的值；独立字段批量执行。
- `expand`：初始观察到的添加按钮 ref，以及期待出现的新分组名。
- 依赖的选择放在下一 `fill` 阶段；执行器只等待指定字段可编辑、指定选项可用。每阶段最多等待 1 秒。

总预算 8 秒，在步骤/动作之间检查；不能强行中断页面自身同步阻塞的事件处理器。初始快照过期、歧义、未经计划允许的新字段、控件类型改变、填写失败、最终回读不一致都会停止。控件在预期更新后重新观察，按精确语义绑定，再沿用旧执行器的实际节点检查。部分执行没有自动回滚，重试前需要检查。

最终检查覆盖所有阶段的目标，能够发现较早阶段的值后来被清空。仍不保证任意延迟的业务/服务器校验已完成。计划仅覆盖当前页面内已能说明的结构，未知字段含义需要交回宿主。

## 测量方法与边界

完整宿主实验使用包含两段教育经历的 14 字段虚构表单，第二段需要点击添加后才出现。三种方式各跑三次，按 refs/plan/script、plan/script/refs、script/refs/plan 轮换位置；各组每次从相同空表单开始。

| 方式 | Codex 能用的填写工具 |
|---|---|
| refs | 原有 `form_fill`，允许批量独立字段，也允许最后一个动作添加行 |
| plan | `form_execute_plan`，一次提交有依赖顺序的阶段 |
| script | 测试专用 `browser_script`，Codex 生成整段异步 DOM JavaScript，在页内处理动态行 |

所有组都先观察，最终再独立观察一次。相同事实、任务约束、Codex CLI 0.155.1、Node 26.8.1、`--ignore-user-config` 与 `--approve-for-me` 策略；只注入本轮 MCP，关闭 shell/web。复用现有 Codex 登录，没有修改全局配置。使用 CLI 默认模型，无显式覆盖；JSONL 未提供确切的解析后模型名，因此不能保证服务端路由完全相同。

计时从启动 Codex CLI 到其退出，包含启动、模型、工具、审批和退出；浏览器启动、页面加载/连接以及外部 oracle 不在计时内。浏览器已启动，每次 Codex 是新的临时任务。事件时间戳是父进程接收 JSONL 的时间；工具以外的间隔不能全归为模型推理。

`script` 是较强的一次生成脚本对照：没有强制逐字段调用模型，没有人为睡眠，也没有预先给它答案代码。脚本只在独立虚构浏览器页面里运行，页面网络仅允许 fixture 资源；产品 MCP 不提供这个工具。它是 DOM 脚本，不是原生 Codex browser 工具或 Playwright locator 接口，也没有测已缓存脚本的重放成本。

独立 oracle 在宿主退出后核验全部 DOM 值、页面自己的事件状态、原生 validity、提交次数为零。原始尝试全部保存，包括失败；不按成功筛选耗时。本地功能验证另外覆盖普通、联动下拉、重复组，以及失败路径。

## 实测结果

| 方式 | 三次完整耗时（秒） | 中位数 | 工具调用 | 独立校验 |
|---|---|---:|---:|---|
| 逐批 ref 填写 | 49.32 / 36.87 / 39.47 | 39.47 s | 4 | 3/3，14/14 字段 |
| 有界阶段计划 | 33.91 / 31.85 / 29.88 | 31.85 s | 3 | 3/3，14/14 字段 |
| 一次生成整段 DOM 脚本 | 38.16 / 40.47 / 42.51 | 40.47 s | 3 | 3/3，14/14 字段 |

计划相对 refs 耗时减少 **19.3%**（1.24×）；相对脚本减少 **21.3%**（1.27×）。9/9 次全部通过，126/126 个字段正确，零提交。未达到 2× 门槛。

## 解释与下一步

1. **优化层次选对了，但收益有限。** refs 每次已经把第一次填表和添加行合在一个请求中，因此实际是 4→3 次工具调用。工具区间累计耗时中位数从 7.74 秒降至 4.63 秒；这些区间包含工具传输和自动审批，不等于 DOM 执行时间。计划执行器本身没有更快。
2. **脚本对照也只有 3 次调用。** 它的工具区间中位数 3.89 秒，比计划更短；完整任务却稍慢。输出 token 中位数为脚本 716、计划 521，生成代码/上下文处理/服务波动都可能影响总耗时。不能把全部差异归因于少一次模型回合，也不能由三次样本给出显著性结论。
3. **薄封装尚不是核心优势。** 受约束计划能减少每次编写页面操作代码的负担，但已有成熟脚本接口和可复用辅助函数也可能做到。当前结果不能证明新执行核心优于成熟浏览器方案。
4. **下一项优先验证真实复杂表单。** 将同样的三组方法用于长表单、异步联动、自定义控件和中途失效，记录完整耗时、恢复回合和人工修正。真实站点缺失时，不把扩大合成样本当成真实性替代。若这些场景仍只有约两成收益，应优先轻量工作流/现有浏览器工具；只有观察到稳定的大幅收益或明显更好的恢复能力，才扩大独立执行核心。

本轮没有测原生 Codex browser、已运行的同一会话、缓存脚本重放、陌生站点或真实账号。小样本、单一任务和默认模型路由未知是结论边界。API 表面和参数编码也随方式变化，所以这是端到端方案比较，不是仅改变调用次数的严格单变量消融。用量中的 input_tokens 是各请求累计数，不能解释为独一份上下文大小。


## 与 Jev 的关系

[Jev Ultrafast](https://github.com/browser-use/jev-ultrafast) 将浏览器状态变成结构化动作空间，专用模型选择动作/目标，必要时才让文本模型生成文本；[Codex 集成示例](https://github.com/wy-coliney/jev-browser-use) 则把上层理解和验证留给 Codex。

本轮借鉴受约束动作和局部执行循环。实现是“Codex 预先决定有限阶段，执行器确定性推进”，还不是 Jev 的逐步专用模型决策；没有接入 Jev 服务、复制其源码或继承其宣传中的倍数。精确状态条件等待用于新计划的依赖阶段，底层旧等待暂时保留以避免同时改变多个变量。
