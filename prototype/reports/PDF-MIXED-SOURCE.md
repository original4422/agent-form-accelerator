# Explicit partial text sources from mixed PDFs

2026-09-30. Deterministic local checks and an actual MCP client/server exchange; no model invocation, real CV, recruiting submission, or speed measurement.

The strict default rejects detected images. `AFA_PDF_SOURCE=1 AFA_PDF_ALLOW_IMAGES=1` accepts a PDF whose pages each have extractable text and whose images use ordinary Image XObjects. It extracts only the text. Source `extractionCoverage` and every successful or unresolved apply result's `sourceCoverage` carry `status: partial-text`, unparsed image page/bbox positions, and instructions to report those regions. Context, search and expansion return the same source object. The generated Codex command carries the opt-in to its MCP process.

`complete` retains its requested-target meaning. Even if every visible field has source-backed text, image content remains unread. No image is classified as a harmless portrait by size or appearance, and image-only facts cannot become a source ID or exact quote. Detection of text or absence of a detected image is not a semantic completeness certificate; rendered graphics, reading order and fact attribution are not verified by text extraction.

## Fixtures and outcomes

All people, addresses and dates are fictional. Generated by `bench/pdf/build-mixed.py` with ReportLab 4.4.9 and Pillow 12.3.0; committed inputs are reproducible from that source. The seven new PDFs (eight pages) were rendered with PDFium and visually inspected: portrait, image-only date, scan page, distinct duplicate-name columns and literal `BI` all appear in the expected positions.

The existing all-scan fixture remains rejected. Existing pure-text fixtures produce identical sources with and without the new opt-in. Source-byte changes still invalidate the session before any write. Exact quote and join rules are unchanged.

## Inline-image counterexample and boundary

While generating `inline-facts.pdf`, ReportLab wrapped an ASCII85 image-data terminator as `~\n>`. PDFium renders the image and its date. With pdfplumber 0.11.9 / pdfminer.six 20251230, `page.images` returns zero for this fixture: its parser searches for the contiguous `~>` terminator and reaches EOF. We do not assume visual rendering establishes full PDF specification conformance. The relevant fact is that visible source content was silently absent from the existing detector.

The adapter now preflights decoded page streams and Form XObject streams with the existing PDFContentParser, rejecting the `BI` operator before inline image parsing. It rejects *all* inline images, including normally parsed ones. It does not scan raw bytes for the letters BI, patch installed dependencies, or attempt OCR. A visited-object set terminates recursive Form resources. The source size/page limits and extraction-process timeout remain in force.

This narrow boundary allows ordinary image objects while making the observed omission an explicit error in both modes. More inline formats should only be accepted after the parser and coverage evidence can account for them.

## Verification

`AFA_PYTHON=/path/to/python npm run check:pdf` runs 9 prior source checks and 13 mixed-source checks. Tests include both ordinary/conditional apply paths, unresolved choices, changed source bytes, unchanged pure-text output, generated CLI environment, and an actual stdio MCP exchange that checks prefetched source, context and compact `changes-v1` receipt coverage. This proves the protocol carries the warning; it is not a model behavior evaluation.

The PDF GitHub workflow installs only the pinned extraction dependency and runs these checks without browser, Codex credentials, or an API key. Local generation/rendering packages are not runtime dependencies.
