# 现成 Playwright MCP 的强基线

2026-09-21。测试对象是同一份未映射中文 Markdown 和同一张字段/资料顺序打乱的英文原生控件表单。只使用 Codex 的既有登录。

## 首轮结果

| 方式 | 三次完整耗时（秒） | 中位数 | 宿主调用 | 结果 |
|---|---|---:|---|---|
| 资料绑定原型，预取上下文 | 29.44 / 43.36 / 26.35 | 29.44 s | 1 / 1 / 1 | 3/3 正确 |
| Playwright，现场观察后填写 | 52.71 / 48.65 / 58.10 | 52.71 s | 2 / 2 / 2 | 3/3 正确 |
| Playwright，预取官方快照 | 76.36 / 87.97 / 84.39 | 84.39 s | 3 / 3 / 3 | 3/3 最终正确，各修复一次错误 |

全部 9 次、108 个语义目标正确，零提交。原型相对没有失败恢复的现场观察组，中位耗时减少 **44.1%**（1.79×）。这是单个本地样本和每组三次的测量，不是广泛速度保证。

预取 Playwright 组每次都直接生成 DOM 脚本，把 `label.textContent` 当成可访问名称，结果在 Contact email 的隐藏报错文字处失败。随后观察 DOM 并修复，全部最终完成。该组较慢的结果予以保留，**不把这组三次失败产生的 2.87× 差距用作稳定提速结论**。

这说明减少观察回合有条件：观察信息必须适合随后的操作方式。可访问性快照中的名称不能直接替代 DOM 全部文本。复用成熟的定位/执行逻辑可以减少这种错误；预取本身不保证减少失败后的总调用次数。

## 补强对照

针对已观察到的错误，追加通用提示：使用可访问定位或已观察引用；直接读取 DOM 时排除隐藏辅助文本和装饰；按问题组区分 Yes/No。不提供具体字段对应关系、DOM ID 或答案。原型组获得同一提示。补强组交替顺序各跑三次，所有尝试单独保留。

| 补强方式 | 三次耗时（秒） | 中位数 | 调用 | 结果 |
|---|---|---:|---|---|
| 资料绑定原型 | 27.05 / 33.97 / 26.53 | 27.05 s | 1 / 1 / 1 | 3/3 |
| Playwright，预取＋通用标签提示 | 53.48 / 50.09 / 56.55 | 53.48 s | 2 / 2 / 2 | 3/3，无失败恢复 |

补强后，Playwright 三次均选用自己的可访问定位能力完成填写，随后另一次读取页面内部事件状态。原型则只返回 DOM/native validity 证据，页面事件状态由独立 oracle 在计时外核对。共同提示中“验证事件交付”造成了不同的验证策略，因此 **49.4% 的总耗时差不能当作验证工作完全一致时的提速结论**。原始记录保留，不把这项差异隐藏起来。

## 验证要求对齐的追加对照

两边共同要求：填写调用可以同时返回 DOM/native validity 证据，证据充分时不重复观察；不读取测试专用的内部状态。两边都由同一个独立 oracle 在计时外验证实际事件状态。保持前述通用标签提示和来源引用，没有提供具体字段映射。各三次交替运行，全部最终填对：

| 验证要求对齐后 | 三次耗时（秒） | 中位数 | 宿主调用 |
|---|---|---:|---|
| 资料绑定原型 | 26.98 / 26.36 / 30.86 | 26.98 s | 1 / 1 / 1 |
| Playwright，预取＋通用标签提示 | 41.65 / 103.00 / 104.76 | 103.00 s | 1 / 3 / 2 |

这组结果**不能宣传成 3.82× 正常提速**。仅第一对都一次调用无失败完成，原型 26.98 s，Playwright 41.65 s（该单对减少 35.2%，1.54×）；只有一对，不能当成稳定中位数或普遍收益。

另两次慢的原因分别为：

1. 自动审查拒绝任务范围外的本地 Skill 文件读取；随后又把测试来源引用判为禁止读取的页面内部数据。宿主最后使用上下文中已有的虚构文字直接填写，未绕过拒绝。共三次调用，103.00 s。提示中“来源数据”和“页面内部状态”的区分没有可靠地传递给该次审查，后续应通过明确的本地来源工具消除歧义，不能依靠规避审批。
2. `getByLabel('Contact email', {exact:true})` 定位超时，等待了 30 秒；宿主修复定位后完成，共两次调用，104.76 s。该执行路径的 locator 默认等待并未受适配器的普通 action timeout 按预期约束。这是恢复与超时策略的成本，不能解释成浏览器写字段本身慢。

成功的第一对中，模型输出 token 为原型 261、Playwright 847；主要差别仍包含代码生成。原型页面内执行约 0.313 秒，宿主工具阶段约 5.38 秒；Playwright 工具阶段约 5.24 秒。至少在这对中，差距主要发生在工具阶段以外，进一步支持优先降低宿主生成/决策成本。

本报告合计 21 次任务、252 个语义目标最终正确。加上文档对照与打乱检查，本轮共 30 次任务、360 个目标最终正确；失败调用和恢复耗时全部保留。成功率统计为最终结果，不抹去中途失败。

## 实验的公平性和限制

- 测试 harness 使用 Playwright 1.63.0；官方 MCP 包自身锁定 Playwright 1.64.0-alpha-1789764292000，均连接同一个已有 Chromium。依赖见仓库 package-lock.json。
- 采用锁定的 [官方 Playwright MCP](https://github.com/microsoft/playwright-mcp) 0.0.82，保留其全部 25 个默认工具，包含批量填表和脚本工具。没有强制逐字段调用，也没有要求每次单独验证。
- 这是**补强过的官方工具基线，不是开箱即用基线**。测试适配器在计时内解析同一文档，在工具元数据中提供来源片段，并允许脚本按 ID 直接读值；预取组还在计时内用官方工具生成初始快照。这样避免强迫基线重新生成长段资料。
- 为了让官方页面脚本直接引用来源，仅在虚构本地页面放置 `__benchmarkSource` 副本。它不能作为真实产品把个人资料送入不可信页面的方式；产品来源会话在本地进程持有文档，只发送指定字段的值。基线适配器不含任何字段映射或代填算法。
- 同一个隔离浏览器，页面重置后分别操作。基线经仅监听 loopback 的临时 CDP 连接，并在启动时选择已知的测试标签页；不连接常用浏览器或用户个人 profile。
- 预取基线的工具表面及快照与原型不同，因而这不是只改变一个变量的执行引擎实验。它回答可用任务接口的整体差距；上下文预取单变量对照见 [文档绑定报告](DOCUMENT-BINDINGS.md)。
- 首轮三种模式按轮换顺序运行。浏览器启动/加载在计时外；解析、CLI/MCP 启动、宿主推理、工具和自动审批、最后响应及退出在计时内。官方连接/选页开销也包含在内。
- 同一独立 oracle 在 CLI 退出后核对 DOM、原生有效性、页面实际事件状态和零提交；两边提示都要求最终回读，脚本路径保留至少 120 ms 的稳定窗口。最终结果正确与工具中的每步成功分别记录。
- 各模式读取及返回的信息不同；尤其初始/补强提示中要求事件交付，脚本有能力额外读取 fixture 专用状态，而原型没有提供该能力。这是追加验证要求对齐组的原因，不把其额外调用视为官方工具不可避免的成本。
- 输出 token 首轮中位数：原型 336、现场观察脚本 953、失败修复的预取脚本 1889。这包含所有宿主输出，不能全部解释为工具参数，更不能直接换算为模型推理时间。原型一次调用也有 26–43 秒波动，显示外部服务/调度与上下文影响不可忽略。

## 对产品方向的意义

当前更有证据支持的价值是**来源引用、可靠字段观察、可复用的批量执行和结果证据**，让模型主要决定语义对应关系。不能由这里推导出“自研浏览器引擎本身更快”。此前 [已有可复用脚本](SOURCE-REFERENCES.md) 与来源引用的耗时接近，这条强反证仍有效。

完整目标尚未完成。下一步必须在真实框架和复杂控件上验证收益及恢复能力，保持成熟脚本对照；不要再以相同的小型原生表单反复测量替代产品验证。
