# 在线草稿的 Codex 端到端对照（2026-09-30）

三种控件变体各完成一组正确配对：原型比官方 Playwright MCP 的完整 Codex 运行时间减少 **33.4%–37.6%**。六次运行的服务器草稿均保存了全部 13 个来源值、两段教育经历和唯一一段选答作文。官方脚本没有失败恢复；本轮差距来自更少的模型往返及脚本生成，而非超时造成的劣化基线。

这是同一业务表单的三种控件实现，每种仅一组配对。已经回答“在线保存和动态问题存在时，批量语义执行是否仍有收益”；原三种真实招聘系统、重复采样中位耗时减半的目标仍待验证。

## 实验如何保持对照

- 共用同一份未映射中文 Markdown 资料和任务提示；初次观察与来源均预取。国家保存后由服务器新增工作许可问题；第二段教育经历需要点击添加。
- 原型使用现有 `browser-controller`、bindings MCP 和 Playwright 后端；官方使用 `@playwright/mcp`，保留全部工具及可批量执行的 `browser_run_code_unsafe`，脚本获得相同来源参数。
- 顺序为 native 官方→原型、Radix 原型→官方、search 官方→原型。每次新建服务与隔离浏览器，模型不能访问服务器 oracle，只能操作公开页面。使用当前已登录 Codex CLI；没有新增模型 API Key。
- 真实 HTTP 草稿保存与目录检索：国家保存延迟 500 ms，其余保存 90 ms，目录返回 180 ms。服务端检查版本并按实际接收值建立 oracle。模型不调用应用 API；写入由页面自己的事件处理器发起。
- 运行环境：Codex CLI 0.155.1、Node.js 26.8.1、Playwright 1.63.0；依赖版本由 `package-lock.json` 固定。当前账户默认模型配置并非跨日固定的实验变量。

## 减少了哪些等待

原型三次均先返回 `FORM_CHANGED_AFTER_WAIT`，把新工作许可问题交回 Codex；下一次 bindings 请求完成剩余字段、搜索与重复教育组。原生和 Radix 共两次调用；search 在填写成功后另读一次 `form_context`，共三次。

官方原生脚本分三次完成：国家与新题观察、主体与增加教育行、第二教育及作文和校验。Radix 多一次展开选项后的观察；search 多一次搜索目录结果观察，均为四次。逐次检查原始脚本和回执，没有定位错误、重试或超时。

原型输出 token 分别为 615、529、718；官方为 1,284、1,345、1,463。原型本地执行累计约 4.05、4.25、6.49 秒，完整 Codex 运行却为 51.73、55.36、59.53 秒。主要成本仍在执行器之外。结果支持“让已知语义下的搜索、选择、等待、重复组和校验留在一次本地请求内”，没有显示重写浏览器引擎的必要性。

## 保存证据还缺什么

独立 runner 已从真实服务器状态确认本轮全部值正确保存。原型执行器等待观察到的公开 `aria-busy` 转换结束，并回读字段；但回执目前没有把 `role=status` 的最终文本传给 Codex。官方脚本能直接读到 `Changes saved.`，原型最终答复则明确表示工具未提供该状态或服务器接受证明。search 的额外 `form_context` 也没有补出这项证据。

因此，两者本轮最终数据正确性相同，宿主可见的保存确认信息尚不完全相同。下一步先把公开保存状态投影到观察和回执，分别验证“正在保存／已保存／拒绝／未保存”，再做反向顺序的重复采样。不能把 `busy=false` 自动解释为任意网站都保存成功。

## 首次 pilot 如何改变了测试页

[首次 pilot 1790705440283](codex-online-form-1790705440283.json) 保留在提交 `c64040c` 对应版本：原生官方脚本最后一个文本未触发失焦保存，页面却仍显示上一次的“已保存”；填写 Subject 后点击添加教育还会让 blur 保存与 rows 保存竞争。原型两次成功记录也保留，但这批不参与速度比较。

正式对照前修正了具体原因：

1. 文本与 textarea 使用稳定的 `label for` / `id`，标签不随填写内容改变。
2. 页内说明文本在离开字段时保存，并显示独立的未保存状态。
3. 页面把保存串行排队，在实际发出请求时读取最新 revision，避免 blur 与按钮点击同时保存。
4. oracle 允许未选择作文为空或未写入，仍逐项检查全部 13 个必需来源值；写入冲突作为诊断记录，最终成功由真实草稿和可见状态决定。

修正后先通过三种控件的未保存状态、稳定标签、blur/点击队列回归，以及 optional blank oracle 检查；再通过三个完整 bindings 流程，包括动态问题出现时停止旧计划。模型测量完成后同一组检查再次通过。
