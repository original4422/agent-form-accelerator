# React/Radix 动态表单验证

2026-09-21。当前只测 Codex，复用已有登录，不新增模型 API Key。完整目标仍是正确率不下降、完整任务明显提速；本报告不会以局部执行耗时替代全流程。

## 为什么增加这一轮

以前的手写原生 DOM 样本不能证明框架受控输入、组件弹层和异步校验能够工作。本轮新增独立 React 19.3.0 + Radix Select 2.3.7 应用：

- React 受控姓名、邮箱、学校、专业和介绍。
- 三个 Radix Select，选项在 Portal 弹层内，通过公开 ARIA 关系定位。
- 选择国家后，城市控件替换并延迟 240 ms 加载选项。
- 邮箱延迟 700 ms 校验，用 aria-busy 和 aria-invalid 明确提供状态。
- 两段教育经历，初始只有第一组字段，需要 Add 展开。
- 中文 Markdown 原始资料，不含网站字段映射，模型必须现场匹配。

这是真实组件库运行在本地的独立样本，不是任何招聘网站的兼容性认证；异步业务逻辑由本地代码模拟。

## 先发现并修复错误完成判断

[修改前复现](framework-before.json)：页面有三个自定义下拉，观察器全部遗漏；无效邮箱在 **170.5 ms** 被报告为完成，随后 **700 ms** 校验拒绝该邮箱。

新执行器识别 select-only 按钮式 combobox，打开明确关联的 listbox，仅选择精确且唯一的可用选项。对于标明校验中的字段，等待 busy 结束再检查 invalid；已正确输入的值不会反复重写来重置验证。

[16 项新增检查](framework-checks.json) 全部通过，包括：React 状态实际收到输入、Portal 选项选择、依赖控件替换、延迟通过和拒绝、busy 超时、缺失/禁用/重复选项、鼠标模式后的键盘选择、disabled fieldset、未知类型停止，以及重复组的来源绑定。其余 53 项功能/MCP检查也全部通过，合计 **69 项**。

有效邮箱的检查约 841 ms 后完成；拒绝邮箱约 770 ms 后返回 VALIDATION_FAILED。这是等待明确状态后的正确结果，不把更早返回当成完成。

## 原始资料和重复组

`repeatGroups` 接受现有组的字段 refs 作为模板，绑定另一段资料的来源 ID，并给出新组的精确名称和已观察的 Add 控件。运行时展开后，要求标签和类型与模板一致；新字段类型改变会停止。使用模板只适用于明确重复的结构，未知含义仍需要宿主判断。

同时保留 `form_expand`：先展开并返回新上下文，再绑定。这两种模式使用同一资料解析器、填表执行器和独立 oracle，适合隔离一次宿主往返的成本。

## 宿主实验

两种绑定方式的初始对照已经完成：

| 方式 | 三次完整耗时（秒） | 中位数 | 宿主调用 |
|---|---|---:|---|
| 先展开，再绑定填写 | 33.88 / 33.28 / 31.68 | 33.28 s | 2 / 2 / 2 |
| 一个请求复用模板并填写 | 24.29 / 23.34 / 24.60 | 24.29 s | 1 / 1 / 1 |

六次全部正确，模板方式中位耗时减少 **27.0%**（1.37×）。输出 token 中位数为 278 与 253，变化较小；主要干预是合并一次宿主往返。本地仍会反复观察依赖、展开和校验，没有省略这些步骤。小样本不提供稳定性能保证。

[修正资料传递、完整快照并加入对称局部循环提示的配对记录](codex-framework-1789947226460.json)：

| 方式 | 三次完整耗时（秒） | 中位数 | 宿主调用 | 首次调用失败 |
|---|---|---:|---|---|
| 来源绑定 + 重复组模板 | 24.12 / 24.64 / 26.81 | 24.64 s | 1 / 1 / 1 | 0 / 3 |
| 官方 Playwright，每次生成脚本 | 140.18 / 131.30 / 136.42 | 136.42 s | 3 / 2 / 2 | 3 / 3 |

六次最终全部正确，共 60 个目标、零提交。三次官方脚本均在打开国家下拉后，用默认 `getByRole('combobox', {name: 'Country of residence', exact: true})` 重新获取触发器的 `aria-controls`，遇到相同的 30 秒 `locator.getAttribute` 超时。Radix 弹层打开时把背景表单标为 `aria-hidden`，默认角色定位因而找不到触发器。恢复脚本改用包含隐藏节点的定位读取元数据，之后完成填写。运行时保留实际节点引用，因此没有触发这个问题。摘要见 [失败记录](framework-official-errors.json)；完整原始日志保存在忽略的本地 private 目录中。

这个差距包含真实的代码生成和恢复代价，**不作为稳定 5.5× 提速或执行引擎更快的证据**；该组没有双方第一次调用均成功的配对。Playwright 输出 token 中位数 2682，原型 249；首次工具调用事件到达中位时间分别约 46.65 s 与 13.76 s。后者包含启动、模型、排队等多种因素，不能全部归因于推理或生成速度。本地原型实际执行约 0.878 s，继续削减这部分也无法把约 25 s 的完整任务减半。

所有模式均包含 CLI/MCP 启动、Markdown 解析、模型匹配、工具、审批、恢复和退出；浏览器启动、bundle 构建及页面加载不计入。宿主以 DOM/native/ARIA 校验为证据，独立 oracle 在计时后核对 React 内部状态、全部 DOM 值、两段经历、弹层已关闭、验证已完成和零提交。使用同一个已登录 Codex CLI 默认模型配置；JSONL 未提供可核实的精确模型版本。当前源码与依赖指纹见 [测量清单](source-hashes-framework-measured.json)。

## 对第一性原理判断的更新

完整耗时的主要可优化部分是宿主往返、模型生成参数/代码，以及错误恢复。页面等待中有不可消除的业务工作，本例 700 ms 校验必须等；更早返回曾产生错误成功。因此“减少模型往返”应当指减少重复语义决策，而不是取消本地观察、状态等待或校验。

重复组模板在同一运行时内把两次请求合并为一次，27% 的收益较直接地支持这一方向。官方工具对照则暴露另一个变量：原型使用已经调试的控件实现，而基线要求模型每次重新写脚本。下一项应给予 Playwright 同样已审核、与具体页面字段无关的通用 helper，让模型只传来源映射。若两者接近，产品价值应聚焦任务接口、资料传递和可靠性；不能再声称自研浏览器底层天然更快。

## 官方基线的接入错误

[初始记录](codex-framework-1789945976944.json) 中两种绑定方式的结果有效；其中官方工具基线有以下接入问题，不用于提速比较。

首个适配器试图让脚本通过动态 import 读取显式提供的 JSON 资料文件。预检返回 ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING；已安装的官方工具实现使用仅提供 page 的 VM context，没有配置 dynamic-import callback。该适配器无法兑现承诺的资料引用能力，其结果不能用于速度比较。原始尝试保留，模型可能通过手工转抄资料恢复，但这不构成公平基线。

修正版本在本地适配器中调用官方工具，把模型函数包装为 `async(page, source)` 并传入同一解析结果。官方浏览器工具、定位、批量及执行能力不变；适配器没有页面字段映射或填写代码，也不向网页全局变量放置来源资料。所有传入值都通过 JSON 序列化，仍是数据。

随后还发现第二个测量问题：`browser_tabs select` 只返回标签列表，适配器错误地把它当成了页面快照。[来源参数版本的三次尝试](codex-framework-1789946570053.json) 因此先做一次必要的页面观察，再分步处理下拉，每次五个宿主调用；不能把首次观察说成多余，也不能与预取完整表单的原型作同条件比较。

[局部循环提示的中止批次](codex-framework-1789946825989.json) 在确认该问题后停止；其中进行中的官方工具行包含取消和 oracle 不可用的影响，不作为正常任务失败或速度样本。已经保存的原始结果保留。

现在显式调用 `browser_snapshot`，并在 [预检](framework-preflight.json) 中断言工具元数据确实含有表单字段、来源第二参数可以读取、重复组 schema 正确。每次正式尝试先做无填写的预检，随后重置页面，再开始 Codex 计时。预检不提供字段映射，不传递任何预先填写结果；正式 MCP 启动仍重新解析文档并获取快照。驱动也支持 SIGINT/SIGTERM 正常保存部分记录及关闭浏览器。

## 参考和边界

[React 受控输入文档](https://react.dev/reference/react-dom/components/input) 是使用真实受控状态的依据；[Radix Select](https://www.radix-ui.com/primitives/docs/components/select) 提供按钮、Portal、选择项与键盘交互；[WAI-ARIA combobox 模式](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) 用于约束组件关系与交互。本实现只覆盖所测试的 select-only 模式，没有实现完整可访问名称算法或所有 ARIA 组件。

下一步先补上述可复用 helper 对照，再增加独立实现和真实招聘流程，尤其输入型搜索建议、文件上传和跨页状态。当前功能和测量不足以证明至少三类不同实现上稳定两倍提速。
