# 原型验证结论 · 2026-09-21

**共享填表工具已跑通；当前证据不支持“比现有合理批量方式快两倍”。暂不将其作为已验证的提速产品发布。**

## 已完成的验证

- 真实 Chromium 加载扩展，通过本地连接执行；标准 stdio MCP 握手、工具发现、调用通过。
- 普通资料、动态依赖下拉、重复经历三类表单；12 项功能检查通过。
- 三种执行方式 × 三类表单 × 五次重复，共 45 次计时运行，全部通过独立页面状态核对。虚构资料共 645 个目标字段填写，全部正确；无提交。
- Codex 实际模型调用成功：`form_inspect → form_fill → form_inspect`，20/20 字段的 DOM 与页面事件状态一致。
- Claude Code 的配置与工具协议已准备，真实模型测试因 OAuth 过期、无法刷新而停止，不能标为通过。

## 执行层结果

单位：中位毫秒；每组 5 次。

| 场景 | 单脚本 Playwright 批量 | 当前扩展批量 | 扩展相对脚本耗时 |
|---|---:|---:|---:|
| 普通资料，20 字段 | 118.1 | 162.6 | 1.38 倍 |
| 依赖下拉，9 字段 | 184.1 | 197.3 | 1.07 倍 |
| 重复经历，14 字段 | 73.6 | 232.7 | 3.16 倍 |

扩展比逐字段对照快约 2.46–5.89 倍，但逐字段对照每次都执行相同的等待/校验，这种收益不能冒充相对实际 Coding Agent 的提速。对更强的单脚本基线，当前扩展没有速度优势。

双方的驱动程序都预先知道目标字段和值；Playwright 脚本还包含控件类型及依赖规则。这里不测陌生表单理解、脚本生成成本或真实网站的通用性。详见 [原始数据](executor-benchmark.json) 和 [计时范围](executor-benchmark.md)。

## Codex 实际调用

成功运行总耗时约 **30.92 秒**，包含 CLI 启动、宿主处理、模型往返、工具审批和调用；其中页面内实际填写与回读约 **159.3 毫秒**，两次观察约 2.3/0.8 毫秒。该简单任务中，执行 DOM 操作只占总耗时很小一部分；其余时间尚未逐项分解，不能全部归因于模型推理。

首次尝试能读取页面，但非交互模式的工具审批策略阻止了写入。第二次使用 Codex 官方 `--approve-for-me` 自动审查流程，通过了对本地虚构表单的填写审批；没有禁用审批或修改全局配置。两次尝试均保留在 [宿主记录](host-smoke.json)。

Claude 的首次尝试在调用模型前返回 `OAuth session expired and could not be refreshed`，没有执行任何填写。完成 Claude Code `/login` 后，可运行 `node prototype/bench/hosts.mjs claude` 补测。

## 下一步判断

1. 在一个用户实际招聘页上，记录现有 Agent 的观察次数、填写/选择/新增经历次数、重试次数和完整耗时。先确认真正慢在哪里。
2. 用相同资料和任务比较原生批量用法与当前工具，计入资料映射、页面校验、失败恢复和人工修正。
3. 若瓶颈是复杂控件导致反复观察与试错，优先验证可复用控件处理；若原生批量已经足够快，则重新评估本项目的独立价值。

日常已登录 Chrome 的扩展安装流程、真实招聘页、自定义控件、跨页、附件上传、Claude 真实模型执行与完整两倍速度门槛仍待验证。
