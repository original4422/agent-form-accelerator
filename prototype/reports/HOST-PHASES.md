2026-09-21；Codex CLI 0.155.1；批次 `1789954486688`。

同样的 59 个来源绑定、同样的离线真实 Lever 页面、guard 后端。3/3 首次工具调用成功，DOM 与原生 FormData 的 25 个正向目标及完整布尔集合均正确，零提交。这里诊断宿主耗时，不做新旧版本的提速比较。

工具元数据在启动后 1.293–2.035 秒已从 MCP 发出。单请求排队只有 0.9–1.2 ms。浏览器控制器的 goal 耗时约 2.2–2.3 秒，和 handler 区间相符。此前把工具区间减去浏览器执行时间得到的 7–9 秒残差，现在能定位到 **handler 收到调用之前**。大结果通过本地 stdio 返回没有出现秒级停顿。

## 结论与无法推出的结论

- 当前主要成本不在 Playwright 输入或浏览器本地执行。即使将约 2.3 秒完全降为零，对约 48 秒的中间样本也只有约 5% 的改善空间。
- 工具调用次数已经为一，但一次调用之前仍要读上下文、选择字段和生成参数；工具完成后仍有宿主阶段。调用数是一项指标，不是延迟本身。
- 7–9 秒处在 CLI 事件和 MCP handler 之间，不能仅凭时间边界认定为模型推理、网络或自动审批。CLI 的 `--approve-for-me` 确实启用自动审查，本实验没有审查内部时间戳，因此不分摊其成本。
- 没有绕过权限或将自动审查关掉。CLI 参数、登录、默认模型选择均与此前相同；事件没有暴露已解析的具体模型版本，不能给它编造模型标识。
- 输入 token 汇总可能涉及多个宿主阶段和缓存；本报告不拿这些统计反推单次推理耗时。

下一项干预是让工具接口对应实际决策：共享同题的重复元数据，以及用一个完整复选集合代替几十个重复的来源绑定。浏览器仍展开成相同的逐字段目标并校验。相同填写范围对照见 `DECISION-CONTEXT.md`；不能提前以参数字节减少推断用户等待减少。

## 测量与复现

`node prototype/bench/codex-host-phases.mjs`

- CLI 以单调时间记录 JSONL 事件收到时间；启动绝对时间为 `performance.timeOrigin + performance.now()`。
- MCP 同机记录启动、预取、handler 收到/排队/完成、序列化、stdio 发送边界；控制器记录请求收到与执行完成。回调只写阶段、工具名、序号、字节数和时间戳，没有源文档、参数、授权令牌。
- stdio send done 不等于宿主实际读取；表中终点使用 CLI 收到的工具完成事件，事件缓冲仍是边界精度的一部分。
- 页面只读加载和预检排除；实际 CLI 启动、MCP 预取、宿主调用、结果回报和退出计入。页面加载后、任何虚构填写前完全断网；没有服务器接受证明。
- 原始宿主日志保存在忽略且私有的 `reports/private/`，公开测量在 `reports/codex-host-phases-1789954486688.json`，源指纹在 `reports/source-hashes-host-phases-measured.json`。后续会变化的五个文件归档于 `reports/source-snapshots/host-phases-measured/`。
- 仪表化后原发现功能的三个实际 MCP 场景全部通过。三个计时样本阶段齐全、时间有序；测量中无并发浏览器负载或源码修改。
