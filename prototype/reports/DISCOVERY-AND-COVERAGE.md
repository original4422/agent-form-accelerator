# 批量发现选项，同时报告未解决的必填项

2026-09-21。仅使用已有 Codex 登录，没有增加模型 API Key。

## 解决的两个问题

上一轮把来源文字、搜索词和目标标签合为一个字符串。城市中文名、学校简称或带校区的选项不能精确相等时，返回模型之后也没有可用的改写查询接口。本轮增加可选 `form_search`：搜索词用于发现，最终值只能来自实际观察的选项。

另一个问题是 `complete` 原来只证明传入的目标完成，不能说明整张表已填好。现在保持该目标级语义，并显式返回 `completionScope: requested-targets` 和 coverage。coverage 根据本会话的来源绑定及当前回读值，列出尚未覆盖的可见必填问题、未支持控件和观察限制，不把既有预填文字视为已经核实，也不声称服务器或隐藏步骤完成。

## 新的工作流

1. Codex 从未映射 Markdown 与页面含义决定哪些选项需要发现，一次提出多个 `{ref, sourceId, query}`。
2. 本地逐项搜索、等待、收集实际选项并关闭弹层，保持之前的选择；不选择任何新项。一次发现最多 12 项，总预算 8 秒，单次控件就绪预算仍为 1.5 秒。
3. 返回可见完整标签及 optionRef。引用绑定到原字段的标签、分组、类型和来源片段；刷新上下文使旧引用失效。
4. Codex 根据全部资料（包括校区）选择 optionRef，并绑定普通字段、重复组。运行时用原查询再次检索，只有目标完整标签仍唯一且可用才选择。重名且没有可见区分信息的项仍然拒绝，不把数组索引当作稳定实体身份。
5. 回读后报告目标级完成情况和剩余必填问题。有资料的字段可以完成，没有资料的到岗日期仍保持空白。

此实现需要第二次模型语义决策时会保留该决策，没有试图通过删除检查获得一条调用。模型也可以并发发出多个单项搜索；MCP 服务端按顺序处理共享标签页/来源会话，避免快照与选项注册表竞争。工具调用数不是模型推理轮数的精确替代。

## 独立样本与正确性

`alias-form.html` 使用上一轮真实 React Select 组件，另换为英文规范标签。资料包含中文校名、英文校名和校区，页面提供同名学校的 Shenzhen / Nanjing 两个校区。搜索服务仅接受索引词，所以用最终带校区的显示文字重新搜索也不能替代原查询。新增一个资料没有回答的必填到岗日期。

应用保存城市、学校实体 ID，独立 oracle 要求第一所学校是深圳校区的 ID；显示相似但错误校区会失败。10 个已知目标必须正确，到岗日期必须为空，搜索文字清空、无待完成查询、无打开弹层、零提交。

- [12 项新功能检查](discovery-checks.json) 全部通过：选项引用来源约束、跨刷新失效、重查询拒绝消失/重复项、保持已有选择、批量预校验、多个查询共存、部分完成与动态失效覆盖。
- [3 项实际 MCP 检查](discovery-provider-checks.json) 全部通过：单项、批量及同时发来三个单项请求；真正填写后核对实体 ID 和唯一缺失必填项。
- 原搜索流程 15 项回归通过；文档流程 8 项回归通过，并增加了不同单选问题的覆盖判断断言。

## Codex 内部对照

同一资料、页面、执行器、提示、核验和默认模型配置，只改变发现接口的粒度。允许宿主合并决定或并发请求，不强制每项经过一次模型思考。

首批 `1789950892350` 使用同一个 queries 数组，单项模式限制 maxItems=1。三个单项任务都先发出三项数组，被 schema 拒绝后恢复；最后均正确。这个接口设计会诱导误用，不能把错误恢复当作干净的批量收益。保留[首批全量记录](codex-discovery-1789950892350.json)及[三个参数错误](discovery-pilot-errors.json)。

修正单项入口为明确的 `{url, ref, sourceId, query}`，批量仍为 `{url, queries}`；重新通过实际 MCP 检查，再冻结代码运行三组交替配对（`1789951414848`，singular-v2）：

| 配对 | 单项发现 | 批量发现 | 完整耗时变化 |
|---|---:|---:|---:|
| 1 | 51.42 s | 44.68 s | 减少 13.1% |
| 2 | 45.22 s | 45.67 s | 增加 1.0% |
| 3 | 53.57 s | 36.00 s | 减少 32.8% |
| 中位数 | 51.42 s | 44.68 s | 减少 13.1% |

6/6 最终正确，60 个已知目标通过独立应用状态核验，零提交，零失败工具调用。单项每次 3 次发现 + 1 次填写，批量每次 1 次发现 + 1 次填写。人工逐条复核六份最终文字：都明确说明到岗日期缺失并保留空白，没有把目标完成说成申请已完成。

工具返回的总字节数中位由 23,482 降至 12,959；但总耗时没有随调用数减半。事件日志中三个单项工具连续出现，不能据此声称减少了两次独立模型推理。JSONL 接收时间也不能区分纯推理、审批、协议排队；`executionMs` 只覆盖最后填写阶段（约 2.01–2.06 s），不包括之前的发现阶段。记录使用 Codex CLI 0.155.1 与已有登录/默认配置，日志没有暴露精确解析后的模型名。

结论：批量发现降低了协议开销和重复上下文，但在这个需第二次语义判断的任务上，完整中位收益只有约 13%，且有一组略慢。三组样本不足以保证稳定收益，更不支持两倍宣传。下一步应增加真实任务代表性，而不是继续调整这个样本追求倍数。

**这是内部接口消融，不能当成对外部成熟产品的提速倍数。** 浏览器加载和无填写的元数据预检在计时外；CLI/MCP 启动、解析、语义判断、工具、审批、错误恢复和退出都计时。最后的独立 oracle 检查 10 个已知目标与保留空白的必填项；同时记录工具返回的 coverage 和宿主最终说明。

## 测量后发现并修复的语义漂移

两个针对性检查复现了错误：搜索结束 blur 时字段改名，仍返回可选择候选项；新增重复组时旧字段改名，旧候选项仍被接受。保留[初次失败](discovery-drift-initial-failures.json)。现在发现结束时复查字段含义，并把每个 optionRef 绑定到发现时的 group/label/kind；后续引用必须匹配。两项[漂移回归](discovery-drift-checks.json)通过，12 项发现检查与 3 项实际 MCP 检查也重新通过。

时延属于上述保护加入前的代码。两个被修改的实测文件已归档，源码指纹有明确映射；最终保护版已测功能，没有重新计时。稳定样本中没有发生字段改名，因此不能以这次补丁冒充另一轮速度结果。

## 边界

optionRef 表示观察过的可见选择，并非网站服务器的稳定实体 ID。复查能防止选项消失、被禁用或变得歧义，但相同可见语义被网站重新绑定到另一个隐藏实体时，DOM 证据不足以发现。独立 oracle 仅用于本地验证，不供执行器读取。

coverage 只覆盖当前可见且未禁用范围内的 required 字段；iframe、shadow DOM、隐藏步骤和服务器接受仍在范围外。可选问题没被填写也不因此获得来源核实。真实招聘平台尚未执行填写/上传/提交，本轮不改变完整目标的验收门槛。
