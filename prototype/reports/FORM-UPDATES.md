# 服务器等待可以留在工具内，未完成的更新不能忽略

2026-09-21。新增被动更新跟踪和批内等待。真实页面只验证失败，本地受控服务验证成功/延迟/失败/动态题目。不是完整申请或速度倍数结论。

## 新证据修正了旧结果的适用范围

真实冻结 Ashby 页面，地点选中后仍显示完整名称，但更新失败。新增 backend 跟踪器在同一公共目录精确回放中捕获 `FORM_UPDATE_NETWORK_FAILED`，没有解除网络冻结，也没有伪造写入成功响应。

重新运行六目标确定性检查时，原先的成功断言失败：**输入姓名就触发 ApiSetFormValue，path 为公开系统字段 _systemfield_name**。更新被阻止后姓名仍在输入框中；新执行器在邮箱、按钮和段落之前停止。更新后的边界断言通过：complete=false、六目标均 unresolved、已验证必填数0、按钮点击0、上传/提交0、传输 socket0。请求记录不含申请值、认证头、cookie 或 formRenderIdentifier 值。

原成功报告保存在 `ashby-pressed-check-pre-update.json`；本次旧断言失败保存在 `ashby-pressed-update-initial-failure.json`；新失败边界的通过结果在 `ashby-pressed-check.json`。历史两次 Codex 的6/6只表示当时 DOM/原生控件核对正确，不能用作在线更新成功基线。没有删掉或重写它们的原始轨迹。

## 最小反例与修复

`form-update-check.mjs` 驱动实际 backend 和 goal coordinator。页面先显示输入值，再从本地 HTTP 服务读取更新；独立服务端计数、页面事件和填写顺序作 oracle。成功 envelope 依据已观察 query selection 构造，**不是抓取到的真实成功响应**。

修复前十项均失败：正常/延迟场景后续字段过早写入，HTTP/GraphQL错误及未知响应仍被判完成，新题目/说明没有阻止旧计划。原失败在 `form-update-initial-failure.json`。初版断网 fixture 在返回任何字节前断开连接，Chromium可能重发导致2次服务端请求；之后改为发送响应头再断开以稳定复现单次请求失败，不把浏览器的传输重试当作执行器重写。

修复后初始十项均通过：正常、700ms延迟、连接中断、HTTP503、GraphQL错误、未知 envelope、表单校验错误、超时、新字段、新说明。失败后的 inspect 与重复相同值 goal 仍不能变成完成，输入 change 次数始终1；精简传输保留失败信号。原有81项相关检查通过，另有两项真实冻结边界检查。

模型批次结束后，补充第11项底层fill反例：第一项写完、第二项服务器更新失败，旧primitive仍给第一项verified（上层goal已经会撤销）。失败保存在 form-update-primitive-initial-failure.json；随后把同样保护补到底层回执，11项全部通过。这是模型测量后的额外修复，未重跑那三次模型；前述31文件指纹一致仅指模型批次内，不能说最终代码与测量时逐字相同。

## 接入范围

- `form-update-tracker.mjs` 只观察主 frame、同源固定端点的 ApiSetFormValue mutation。它不发请求，不提供候选/答案。HTTP200不足以通过，还需无 GraphQL/表单错误及符合受限结构的 FormRender；实际站点成功形态若不同，会停止而非猜测。
- 每次观察到更新后，在原8秒目标预算内最多等待1.5秒；收到完整 body 后再等待120ms DOM安静窗口并检查公开题目、选项、必填和说明。同一期间新的已知操作也被等待。无已知请求时不增加该等待。
- 新含义返回 `SERVER_FORM_CHANGED`，后续动作未尝试；失败返回具体固定原因。只检查 DOM 值不再能绕过已知失败，旧 verified 台账清除。
- 失败跟踪在同一个 document 内保留，重新读取context不会清除；不自动重发，导航新文档才重置。状态随模型上下文和回执传出；控制器关闭移除监听。

只适用于已识别操作。未观察到请求不等于不存在服务器依赖；监听安装前的请求、未知端点、任意更晚启动或渲染尚无通用保证。120ms为有界稳定性检查，不能证明未来绝无变化。地点和文件仍未开放支持；真实更新响应也尚未验证。

## 实际 Codex 验证

批次1789973395714，生产 browser-bindings-mcp、现有 CLI 登录和默认模型配置；同一提示、同一两条虚构来源。所有功能检查结束后才启动，31个运行时/fixture/依赖文件 hash 测前测后相同。三次全部保留，无挑选或重跑。

| 本地场景 | 宿主调用 | 实际行为 | 模型任务耗时 |
|---|---:|---|---:|
| 响应延迟700ms | 1 | 一次 apply 等待并完成两字段，服务端请求1次，后续填写发生在渲染后 | 36.441 s |
| 服务端新增必填题 | 2 | 首次 SERVER_FORM_CHANGED；Codex 用新观察继续填写姓名，未填无来源的工作许可，并明确报告 | 113.161 s |
| 连接中断 | 1 | FORM_UPDATE_NETWORK_FAILED；姓名未尝试，报告未完成，没有轮询或重写 | 81.890 s |

三种情况下首字段 change 事件和服务端请求都恰好1次，没有在等待中填下一项。动态场景第二次 complete 仅针对新计划的姓名；最终回答没有将整份申请宣布完成。原始轨迹位于 private，参数/工具状态/服务器和DOM oracle 在 `codex-form-update-1789973395714.json` 及最新同名报告。

工具内部分别约1.155s、0.326+0.192s、0.102s，远小于总体时间；宿主调用时长还包含MCP调度/传输等，不能把全部差值归因于某个模型内部阶段。没有相同正确性基线，三种任务也不同，不能从这些数字计算提速。此次证明的是合理调用边界与失败处理，**端到端36–113秒仍离“明显提速”的完整目标有距离**。

## 第一性原理上的调整

端到端成本依然由模型决策往返、实际浏览器/服务器工作及恢复成本组成。工具可以消除“再等一下、再看一次”的模型轮询，但不能消除确实存在的服务器依赖。可合并的是含义已确定、前提受检查的一段操作；出现新问题后，原先的答案计划不再完整。

因此不应为了少一次调用把未知分支默认为成功。后续完整流程需要在我们控制的在线表单上核对服务器状态和动态题目，再做正确率相同的 Codex 速度对照。冻结招聘页继续用来发现控件和失败边界，无法独自证明在线工作流完成。
