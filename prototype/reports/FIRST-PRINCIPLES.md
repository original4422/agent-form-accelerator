# 为什么当前原型更慢：实现与范式分开判断

日期：2026-09-21。当前只用 Codex 做宿主测试，Claude 暂停。结论依据本地实验，不外推到真实招聘网站。

**结论：局部变慢主要是实现中的等待策略；无法据此推出整个范式错误。但把页面内几百毫秒作为端到端两倍提速的主要来源，优化层级选错了。当前工具尚未证明能减少相对成熟批量方案的模型回合或失败恢复。**

## 1. 先定义真正的目标

用户关心的是：从发出填写要求，到页面被正确填好并完成必要验证的时间，以及修正错误所需的人力。

可用下面的关键路径分解思考（各项可能有重叠，不能把独立统计无条件相加）：

```text
总时间 = 启动/准备 + 串行决策阶段 + 工具调用阶段 + 最终交付
工具调用阶段 = 审批/调度 + 本地传输 + 页面操作 + 必要等待/验证
失败恢复会再次引入观察、模型决策和工具调用。
```

同一页面需要输入多少字段，并不直接决定大模型必须被调用多少次。已知字段和值可以用一个普通脚本批量完成；只有出现尚未解决的语义、未预见状态或权限问题，才可能需要新一轮决策。

## 2. 速度问题可稳定复现

已运行 `node prototype/bench/repro-slowdown.mjs`：重复经历的脚本中位耗时 68.59 ms，原型 243.40 ms；断言按预期失败。

进一步最小化为单个姓名输入：`node prototype/bench/repro-slowdown.mjs --minimal`，脚本 12.87 ms，原型 42.80 ms。一个字段已经足以复现，说明复杂表单、跨站适配不是该局部差距的必要原因。

该命令用于复现未修复的现象，预期可返回非零，不作为当前正确性测试的通过条件。

## 3. 四个假设与消融结果

在临时扩展副本中只改变等待模式/调用路径，真实运行时保持原样。3 类表单 × 7 种方式 × 5 次重复，共 105 次计时运行，全部通过即时的独立页面状态校验。另加延迟拒绝输入的反例，检查快速方案的代价。

单位为中位毫秒；原始数据与全部重复见 [diagnosis-ablation.json](diagnosis-ablation.json)。

| 场景 | Playwright 批量脚本 | 原型 | 原型中等待耗时 | 只保留每批最后等待 | 完全删除等待（仅诊断） |
|---|---:|---:|---:|---:|---:|
| 普通资料 | 108.3 | 162.4 | 144.3（88.8%） | 48.8 | 12.0 |
| 依赖下拉 | 180.5 | 198.3 | 181.4（91.5%） | 169.9 | 94.2 |
| 重复经历 | 67.1 | 235.8 | 218.0（92.5%） | 123.0 | 13.4 |

### 假设 A：固定等待是主要局部开销——成立

`settle()` 至少等 35 ms。选择下拉、单选、复选、添加行以及每批结束时都会调用。普通资料中约 4 次，重复经历中约 6 次；普通字段操作只有毫秒级，等待自然占据绝大多数时间。

原注释称其不是固定逐字段延迟，但它确实对每个上述控件设置了最低等待。命名为“稳定窗口”不会消除这项成本。

### 假设 B：基线少做观察/校验导致主要差距——不是主要数值原因，但比较范围仍有限

给 Playwright 批量脚本前后各补一次相同字段观察后，三类耗时分别为 109.4/187.0/68.4 ms，相对 108.3/180.5/67.1 ms 的变化很小。各方式原本都执行相同的独立页面数据核验。因此漏算观察并不能解释数十到上百毫秒的主要差距。

但这仍不是完全等价的产品比较：脚本预先知道目标控件类型和依赖规则；原型驱动也预先知道字段含义和值；两者均未计入理解陌生表单和生成计划的时间，未测试原生 Codex computer-use 工作流。直接写 DOM 值与 Playwright 模拟输入的事件路径也不同。本地通过不证明真实网站等效。

### 假设 C：扩展桥接本身很慢——在本实验中不成立

保持原执行器与等待策略，用直接浏览器调用代替扩展路径，耗时变成 159.1/195.5/235.8 ms，与扩展的 162.4/198.3/235.8 ms 接近。

扩展路径测得的页面外调用残差中位数约 6–8 ms。这个残差包括调度/序列化等，不是逐包网络测量；该实验未包含宿主 MCP 和审批。但它足以否定“必须先重写扩展/换语言才能解决当前局部差距”。

### 假设 D：优化执行器不会自动减少模型决策——代码与宿主计时支持这一判断

当前协议以观察到的字段引用为操作单位。添加经历后，新字段引用尚不存在，所以执行器返回给调用者，再生成下一批动作。简单文字页面是 inspect→fill→inspect；有动态组时还要多次展开/观察/填写。

一个已经构造好的普通浏览器脚本，同样能在内部循环、等待选项、添加组并核对结果。批量执行不是本项目独有的计算能力。要证明相对它的优势，需要测出更低的规划成本、更少的模型介入/审批、更少的错误恢复，或重复任务的复用收益。

注意：这里比较的是能力与测量边界，不是已经完成了原生 Codex 两组端到端性能对比。

## 4. 删除等待为何不是正确修复

| 页面在填写后拒绝输入的延迟 | 原等待策略报告完成 | 无等待报告完成 | 150 ms 后实际值正确 |
|---|---|---|---|
| 10 ms | 否 | 是 | 两者都否 |
| 100 ms | 是 | 是 | 两者都否 |

第一个反例说明直接删等待会让原本能捕获的异步错误漏掉。第二个反例说明现有“35 ms 没有 DOM 变化”也不是完成证明：`.value` 的变化未必产生 MutationObserver 能观察到的变更，网络校验也可能更晚返回。

正确抽象应是有界、具体的完成条件：目标选项已经出现、控件已可编辑、依赖区域已生成、输入被框架保留、明确校验状态已更新。没有可观察的强完成信号时，应该返回验证边界或保留后续检查，不能把任意超时说成已被服务端接受。

因此，本次没有把“不等待”或“只等最后一次”的实验变体合入运行时。任务是诊断和判断方向，而非通过删掉验证把速度断言变绿。

## 5. Codex 的真实时间分布

本次追加的 Codex 测试 20/20 字段正确，未提交。完整日志元数据保留在 [host-smoke.json](host-smoke.json)，尝试编号 `codex-1789938260656`。

| 阶段 | 本次测量 |
|---|---:|
| 进程启动到退出 | 37.075 s |
| 到首次 MCP 调用开始 | 10.256 s |
| 首次 inspect 工具阶段 | 0.044 s |
| 首次 inspect 返回至 fill 开始 | 14.547 s |
| fill 工具阶段（含审批/调度/传输等） | 4.040 s |
| 其中页面内填写与回读 | 0.162 s |
| fill 返回至最后 inspect 开始 | 2.665 s |
| 最后 inspect 工具阶段 | 0.014 s |
| 最后 inspect 完成时刻 | 31.567 s |

这些是父进程接收 CLI 事件的时间边界，不能精确区分推理、排队、网络和自动审查。`fill` 工具阶段的 4 秒也不能全部算成 MCP 传输，更不能全部算成浏览器执行。CLI 退出比验证完成更晚，因此正式产品实验应同时报告“首次正确填好”“验证完成”和“最终回复”的时间。

本次 CLI 报告累计输入 93,703 tokens，其中缓存输入 68,864；这是多次请求的累计量，不是页面大小，也不是唯一上下文长度。过大的重复上下文可列为后续实验项，当前未证明其与延迟的因果关系。

### 优化收益上限

仅用上一轮 30.920 秒总耗时、0.1593 秒页面填写计时做反事实：保持其他所有阶段不变，即使这部分瞬间完成，也只得到：

```text
最大速度比 = 30.920 / (30.920 - 0.1593) ≈ 1.0052
```

也就是约 0.5% 的上限，而非 2 倍。这个上限只约束“只优化那段页面执行、其他阶段完全不变”的方案；若能减少模型往返、审批次数或错误恢复，收益可以更大。

## 6. 范式判断与建议

- **保留**“Agent 理解意图、确定性执行器操作浏览器”的分工：它有明确的正确性与可测试性价值，当前证据没有否定它。
- **重新定义加速点**：从更快处理每个字段，转向更少地让大模型参与预期内的机械步骤、减少无效观察/重试、复用已验证流程。
- **下一项候选实验**：让 Codex 一次给出含依赖和完成条件的填写计划，执行器在新增行/选项加载等可预期变化中继续运行，只在真正需要新语义判断时返回。优先复用成熟浏览器执行能力，不为毫秒级 DOM 操作再造一套通用框架。
- **必须设置更强基线**：相同 Codex/资料/网站/验证标准/审批设置下，比较“普通优化批量脚本”“当前字段批次接口”“目标级计划执行”。测完整耗时、模型介入次数、错误率与修正次数。若目标级计划对成熟脚本也无优势，应评估是否只适合做轻量 Skill，而不继续扩成独立框架。

这是候选架构方向，尚未替换当前实现；正式取舍见 [ADR-0001](../adr/0001-optimize-host-critical-path.md)。
